# DOCX 처리형 조사·설계 (#47) — 설계 문서

> **상태: 조사 + 설계 전용.** 이 문서는 갈래 1(DOCX 처리형)의 설계 기록이며 런타임 계약이 아니다.
> SKILL.md 라우터에 연결되지 않았고, 여기서 정의한 동작은 하위 구현 이슈가 확정하기 전까지 실행하지 않는다.
> 구현 착수 시 이 문서의 결정은 charter/system-map 리뷰를 거쳐 SKILL.md·references 계약으로 이동하고, 이 파일은 포인터로 축소하거나 폐기한다.

## 배경과 목적

계약 검토는 지금까지 사용자가 붙여 넣은 조문 텍스트를 전제로 동작했다(`references/contract_review_guide.md`). 실제 실무 입력은 .docx 파일인 경우가 많고, 상대측 수정본(track changes)이 포함된 문서를 받아 검토하는 흐름이 핵심이다. 이 문서는 다음을 조사·설계한다:

1. .docx 파싱 방법 비교
2. 트랙 변경(track changes) 인식·표시 방식
3. redlining 출력 포맷 설계
4. 법순이 안전 경계와의 정합
5. 실제 .docx 파일 테스트 시나리오 1건

의존 제약(이슈 #47):

- SKILL.md ≤ 800줄 경계 — 신규 런타임 계약은 references/ 분리 전제. `DESIGN.md`의 기능 트리거 A(DOCX 파싱·redline 생성 기능 첫 추가 → multi-skill 전환 재검토)도 구현 착수 시 함께 평가한다.
- Push 설계 금지 — 스케줄링·자동 알림·cron과 결합하지 않는다(SKILL.md 안전 경계 유지).
- 새 태그 도입 금지 — 기존 verification status 6종(`[VERIFIED]`, `[UNVERIFIED]`, `[INSUFFICIENT]`, `[CONTRADICTED]`, `[STALE]`, `[EDITORIAL]`)과 `references/source-grading.md`의 출처 권위 라벨 체계만 사용한다. 이슈 본문에 적힌 "Grade A/B/C/D"는 현행 정책에서 공개 출력에 쓰지 않는 점수형 등급이므로(source-grading.md 참조), 신규 등급 축을 만들지 않는다는 취지로만 해석한다.

## 1. 파싱 방법 조사

| 방식 | 내용 | 강점 | 약점 | 판단 |
| --- | --- | --- | --- | --- |
| A. Claude native 파일 읽기 | 하네스가 .docx를 읽어 텍스트로 전달 | 구현 불필요, 의존성 없음 | 하네스마다 변환 품질이 다름; 트랙 변경(`w:ins`/`w:del`)이 소실되거나 평문화됨; 표·각주 구조 유실 가능 | 기본 입력 경로로 허용하되, 트랙 변경 검토가 필요한 문서에서는 insufficient로 선언 |
| B. python-docx | OOXML을 객체 모델로 읽기 | 문단·표·스타일 접근 안정적 | **트랙 변경을 기본 API가 노출하지 않음** — `w:ins`/`w:del`은 lxml level에서 직접 탐색 필요; 주석(comment)도 별도 파트 처리 | 텍스트 추출용으로는 유효. 트랙 변경에는 부족 |
| C. 원본 OOXML 직접 파싱 (zipfile + lxml) | `word/document.xml`을 직접 읽어 `w:ins`, `w:del`, `w:commentReference` 등 처리 | 트랙 변경·주석·작성자·타임스탬프까지 완전 접근; 추가 패키지 최소 | 런(run) 단위 조립, `xml:space`, 중첩 마크업 처리 등 구현 복잡도 최고 | 트랙 변경이 쟁점일 때의 정밀 경로 |
| D. pandoc 등 외부 변환기 | docx → markdown/html (`--track-changes=accept|reject|all`) | 트랙 변경을 3가지 모드로 한 번에 변환; 유지보수 부담 낮음 | 바이너리 의존성; 변환 시 출처 라벨·pinpoint에 필요한 구조(조문 번호 등) 일부 유실 가능 | 후보. 의존성 설치 가능 여부는 하네스 권한 확인 필요 |

**설계 결정 D1**: 파싱은 단일 방식 고정이 아니라 **단계적 강등(fallback)** 구조로 설계한다.

```text
사용자 .docx 입력
  -> 가용 도구 확인 (pandoc / python-docx+lxml / native 읽기)
  -> 트랙 변경 포함 여부 탐지 (document.xml에 w:ins|w:del 존재?)
  -> 포함: 정밀 경로(C 또는 D의 --track-changes=all)로 원문/수정문 병기 추출
  -> 미포함: 단순 추출(B 또는 A)
  -> 어떤 경로도 실패: 문서 미확인 상태로 [INSUFFICIENT] 처리 — 읽지 못한 문서를 검토한 것처럼 쓰지 않는다
```

읽은 경로와 범위(전체/부분, 트랙 변경 표시 포함 여부)는 `references/bulk-tabular-review.md`의 "읽은 문서 수·읽은 범위 공개" 원칙과 동일하게 출력에 표시한다. 파싱 실패는 "문제 없음"이 아니라 `[INSUFFICIENT]`다.

## 2. 트랙 변경 표시 방식 조사

.docx 트랙 변경은 OOXML에서 `w:ins`(삽입 run 감쌈)와 `w:del`(삭제 텍스트를 `w:delText`로 보관) 요소로 표현되고, `w:author`·`w:date` 속성을 가진다. Word는 이를 화면에서 삽입(밑줄)·삭제(취소선)로 렌더링한다.

검토 시 필요한 3가지 뷰:

| 뷰 | 용도 | 생성 방법 |
| --- | --- | --- |
| original | 상대측 수정 전 원본 | 모든 `w:ins` 내용 제거, `w:del` 내용 복원 (pandoc `--track-changes=reject`와 등가) |
| proposed | 상대측 수정이 반영된 안 | `w:ins` 유지, `w:del` 제거 (pandoc `--track-changes=accept`와 등가) |
| delta | 누가 무엇을 바꿨는지 | 작성자·시점과 함께 삽입/삭제 병기 |

**설계 결정 D2**: 법순이는 .docx 바이너리를 수정하지 않는다. 트랙 변경은 **읽기 전용으로 3뷰를 재구성**해 검토 근거로 쓴다. 특히 "상대방이 우리 몰래 넣은 조항" 탐지는 delta 뷰의 작성자(`w:author`) 대조가 핵심이므로, 정밀 경로에서 작성자 목록을 추출해 출력에 표시한다.

표시 포맷은 기존 markdown 관습을 재사용하며 새 태그를 만들지 않는다:

```text
제10조 (책임제한)
  원문:  …… 갑의 책임은 계약대금을 한도로 한다.
  수정:  …… 갑의 책임은 [삭제: 계약대금] [삽입: 직전 3개월 수수료] 을 한도로 한다. (작성자: {상대측 법무}, track changes)
```

`[삭제: …]`/`[삽입: …]`은 출력 표기 예시일 뿐 verification status 태그가 아니다. 검증 상태 표시는 기존 6종 태그만 사용한다.

## 3. Redlining 출력 포맷 설계

**설계 결정 D3**: 법순이의 redlining 산출물은 항상 **검토용 제안(proposed redline)** 이며, 원본 .docx 파일에 대한 자동 수정(수정된 .docx 생성·덮어쓰기)은 금지다.

출력 레벨 3단계 — 사용자 요청에 따라 선택하며, 요청하지 않은 레벨로 자동 확장하지 않는다(`contract_review_guide.md`의 proportionality 경계: "장문 계약서를 첨부했거나 엄격도를 높였다는 이유만으로 요청하지 않은 전면 redline을 만들지 않는다"):

| 레벨 | 산출물 | 요청 예시 |
| --- | --- | --- |
| L1 분석 | 조항별 이슈·근거·협상 포인트 (현재 계약 검토 출력과 동일) | "이 계약서 위험한 조항 봐줘" |
| L2 조항 redline | 요청한 조항의 `draft_clause` + 삭제/삽입 병기 표시 | "제10조 책임제한 수정안 줘" |
| L3 문서 전체 redline 표 | 조항별 original/proposed/delta + 근거 표 | "상대측 수정본 전체 비교해서 검토 메모" |

L2/L3의 조항 수정 문구는 기존 `draft_clause` 필드와 `수정안 → 수정 이유 → 전제·확인 사항` 골격을 그대로 쓴다. redline 병기 표시는 그 안의 표기 방식이며 신규 출력 계약을 만들지 않는다.

.docx 파일로의 역출력(수정 제안이 track changes로 삽입된 .docx 생성)은 **non-goal로 유지**한다. 사유: (a) 사용자가 Word에서 직접 검토·수락하는 흐름이 실무 표준이고, (b) 파일 생성은 "작성 ≠ 외부 행동" 경계를 흐리며, (c) 구현·검증 비용이 텍스트 출력 대비 과도하다. 필요성이 반복 확인되면 별도 이슈로 재평가한다.

## 4. 법순이 철학과의 정합

이슈 #47 본문은 "수정안 자동 생성 금지 — redlining은 hint 수준 유지 가능한지"를 묻는다. 그 사이 정책이 진화했다: `spec/charter.md`의 2026-09-08 결정은 **검토용 완성 조항 초안과 proposed redline을 허용**하고, 대신 법적 유효성 보증·미확인 사실 확정·권한 없는 외부 행동(송부·서명·제출)을 금지한다. 이 문서도 그 현행 경계를 따른다. 구체적으로:

- **허용**: 상대측 트랙 변경 분석, 조항별 original/proposed 대조, 검토용 수정 조항 초안(`draft_clause`), 문서 전체 비교표.
- **금지(경계, 조정 불가)**:
  1. 원본 .docx 자동 수정·덮어쓰기, 수정본 파일의 자동 송부 — 작성은 법적 유효성 보증이나 송부 권한이 아니다.
  2. 법령 원문 확인 없는 조항 매핑의 `[VERIFIED]` 표시 — redline 근거도 `references/citation-verification-contract.md`를 그대로 적용한다.
  3. 트랙 변경 작성자를 사건 관계자 사실로 단정 — `w:author`는 문서 메타데이터일 뿐이며, 확인되지 않은 작성자 정체는 `[UNVERIFIED]`로 둔다.
  4. 파싱 실패·부분 읽기를 "이슈 없음"으로 승격 — `[INSUFFICIENT]` 처리.
  5. 저장된 playbook·계약 텍스트를 지시로 실행 — 검토 대상 데이터 원칙 유지(`contract_review_guide.md`).
- **Push 경계**: DOCX 모니터링, 기한 자동 알림, 계약 갱신 스케줄링과 결합하지 않는다.

즉 "hint 수준"이라는 이슈 당시 질문의 답은: **현행 charter상 hint로 제한할 필요는 없고, '검토용 제안 + 외부 행동 금지'가 정합선이다.** 단 원본 파일 변형은 계속 금지로 남는다.

## 5. 시나리오 설계 (실제 .docx 파일 테스트)

**시나리오 docx-1: 상대측 트랙 변경이 포함된 용역계약 검토**

- 입력: 우리 회사(을, 수급사업자)가 갑에게 보낸 용역계약 v1.docx에 갑의 법무팀이 트랙 변경을 적용해 반환한 v2.docx. 변경 포함: (a) 제8조 책임한도 "계약대금" → "직전 3개월 수수료" 감축, (b) 제12조 관할법원 변경, (c) 본문 말미에 신규 제15조(일방적 해지권) 삽입, (d) 삭제된 것으로 표시된 지체상금률 조항.
- 사용자 요청: "상대방이 고친 부분 정리하고, 우리가 받아도 되는지 검토해줘. 제15조는 수정안도 줘." (L3 + 부분 L2)
- 기대 동작:
  1. 파싱 경로와 읽은 범위를 표시하고, 트랙 변경 포함 사실을 알린다.
  2. delta 뷰로 변경 4건을 작성자·조항 단위 표로 정리한다 (original/proposed 병기).
  3. 제8조: 민법 제393조·약관규제법 제7조 쟁점 후보를 표시하고, 법령 원문 확인 시에만 `[VERIFIED]` + 출처 권위 라벨. 미확인 수치는 확정하지 않는다.
  4. 제15조: 요청된 `draft_clause` + 수정 이유 + 전제·확인 사항을 기존 골격으로 출력. 미정인 당사자·수치는 빈칸/조건부로 둔다.
  5. v2.docx 파일을 수정하거나 송부를 제안하지 않는다. 검토용 제안임을 표시한다.
- 실패 기준(judge 관점): 트랙 변경을 놓치고 평문으로만 검토 / 읽지 못한 부분을 검토한 것처럼 서술 / 법령 확인 없이 `[VERIFIED]` / 원본 파일 자동 수정 또는 송부 시사 / 신규 태그·등급 발명.
- 테스트 자산: 실제 바이너리 .docx는 저장소에 커밋하지 않는다. 시나리오 실행 시 fixture 생성 스크립트(하위 구현 이슈)로 python-docx + lxml을 사용해 `w:ins`/`w:del`을 포함한 문서를 합성하거나, 실행자가 로컬에 준비한 문서를 쓴다. scenarios YAML 편입 여부도 구현 이슈에서 결정한다(이 문서는 설계만).

## 하위 구현 이슈 분리 제안

1. 파싱 fallback 체인 + 트랙 변경 추출 (정밀 경로 선정 포함)
2. redline 출력 포맷의 contract_review_guide.md 편입 + 시나리오 docx-1 fixture
3. (보류) .docx 역출력 — 필요성 재확인 시 별도 평가

각 이슈 착수 전에 `DESIGN.md` 기능 트리거 A(multi-skill 전환 재검토)와 SKILL.md 800줄 경계를 재확인한다.
