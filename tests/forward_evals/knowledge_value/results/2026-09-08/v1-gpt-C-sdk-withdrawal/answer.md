# SDK 교체 검토 메모(초안)

- 기준일: 2026년 9월 8일
- 대상: 앱팀·개인정보 담당자
- 목적: 맞춤형 광고 SDK 교체 시 철회 처리와 성능 계측의 구분
- 검토 범위: 제공된 법령 스냅샷 및 개인정보보호위원회 자료 발췌에 한정

## 1. 검토 결론

**[INSUFFICIENT] 현재 자료만으로 신규 SDK 전환 후 맞춤형 광고 철회가 전체 처리 흐름에 반영된다고 판단하기 어렵다.**

앱 화면의 “철회 완료” 표시와 신규 SDK의 광고 설정 비활성화는 앱 단 조치가 수행되었다는 증거다. 그러나 서버의 기존 이벤트 수신기가 구매 이벤트를 새 벤더로 전송할 수 있고 실제 전송 로그가 확보되지 않았으므로, 철회 후 서버 측 전송이 중단되었는지는 확인되지 않았다.

벤더의 “suppression 적용 완료” 회신도 다음 사항이 없어 증거 범위가 불명확하다.

- 어떤 식별자·계정·기기를 대상으로 했는지
- 광고 노출, 프로파일링, 데이터 수집, 재이용 중 무엇을 억제했는지
- 적용 시각과 철회 요청 시각의 관계
- 신규 수집만 중단한 것인지, 기존 보존 데이터의 이용도 중단한 것인지
- 일부 요청 실패나 재활성화 조건이 있는지

따라서 화면과 회신만으로 충분하다는 의견은 채택하기 어렵다. 반대로 **모든 이벤트와 모든 보존 데이터를 즉시 삭제해야 한다는 결론도 제공 자료에서는 도출되지 않는다.** 제공된 안내서는 opt-out 이후 미래 데이터 수집 중지를 예시하고, 삭제 기능 및 계약상 파기 조건의 명확화를 권고하지만, 모든 철회 상황에서 모든 데이터를 즉시 삭제해야 한다고 정하지 않는다. 기존 데이터의 삭제·보존 범위는 수집 근거, 처리 목적, 계약, 보존 필요성 및 실제 데이터 상태를 구분하여 판단해야 한다.

권고하는 출시 판단은 다음과 같다.

> 철회 후 서버 전송 및 벤더 처리를 검증할 수 있는 로그·계약·벤더 확인이 확보될 때까지 광고 SDK 교체를 **조건부 승인**하고, 해당 확인을 출시 전 통과조건으로 둔다. 확인 실패 시 철회 이용자의 서버 측 광고 이벤트 전송을 차단한 상태로 출시하거나 전환을 보류한다.

이는 위법 확정이 아니라, 현재 증거 부족에 따른 내부 위험 통제 판단이다.

## 2. 현재 증거로 가능한 판단

| 항목 | 현재 판단 | 근거·한계 |
|---|---|---|
| 앱 화면의 철회 처리 | 앱 UI에서는 완료 표시가 되고 신규 SDK 광고 설정도 꺼짐 | 클라이언트 단 상태만 확인된다. 서버·벤더 처리까지 증명하지 않는다. |
| 서버 이벤트 전송 | **[INSUFFICIENT] 중단 여부 판단 불가** | 전송 가능한 경로가 남아 있지만 실제 로그가 없다. 전송됐다고도, 안 됐다고도 확정할 수 없다. |
| 벤더 suppression | **[INSUFFICIENT] 범위·시점 불명확** | 대상 식별자, 목적, 적용 시각 및 기존 데이터 처리 여부가 회신에 없다. |
| 벤더의 독자적 광고 최적화 | **[INSUFFICIENT] 판단 불가** | 계약상 허용 여부가 확인되지 않았다. |
| 즉시 전면 삭제 의무 | 제공 자료만으로는 확정할 수 없음 | opt-out, suppression, 삭제는 서로 다른 조치다. 제공 자료에는 모든 경우의 즉시 전면 삭제 규칙이 없다. |
| 개인정보 국외이전 | **[INSUFFICIENT] 해당 여부 판단 불가** | 벤더 서버 위치, 해외 접근 및 보관 지역이 제공되지 않았다. |
| 성능 계측 | 확인된 구조가 유지된다면 광고 철회와 별도 처리 가능 | 비식별·비재식별 집계값만 내부 처리하고 외부 전송과 개인·기기 식별자가 없다는 사실을 전제로 한다. |

## 3. 법적·실무적 판단 기준

개인 또는 기기를 식별할 수 있는 행태정보를 처리한다면 적법한 수집 근거와 사후 거부 기능이 문제된다. 랜덤 식별자라도 다른 정보와 누적·결합하여 개인을 알아볼 가능성이 있으면 개인정보에 해당할 수 있다. 반대로 개인정보가 포함되지 않고 합리적으로 다른 정보와 쉽게 결합해 개인을 알아볼 수 없다면 개인정보로 보지 않을 수 있다.  
**[공식 실무자료 발췌] [VERIFIED: 제공 발췌 대조]** — 개인정보보호위원회, 「맞춤형 광고에 활용되는 온라인 행태정보 보호를 위한 정책 방안」(2024.1), PDF 22·25쪽. 현재 벤더 시스템에 대한 사실 판단은 별도다. [원문 게시 페이지](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=9888)

개인을 식별하지 않는 행태정보로 처리하려면 개인정보 처리 시스템과의 분리, 매칭키 부재, 누적·중첩·결합에 따른 식별 가능성 방지가 중요하다. 맞춤형 광고 거부 후 다른 식별자나 디지털 지문을 만들어 거부를 우회해서는 안 된다는 정책 방향도 제시되어 있다.  
**[공식 실무자료 발췌] [VERIFIED: 제공 발췌 대조]** — 같은 정책 방안, PDF 25~26쪽.

벤더가 회사의 지시에 따라 개인정보를 처리하는 수탁자라면, 제공된 법령 스냅샷상 위탁 문서에는 목적 외 처리 금지와 보호조치 등이 포함되어야 한다. 위탁자는 수탁자의 처리 현황을 점검·감독해야 하며, 수탁자는 위탁 범위를 넘어 개인정보를 이용하거나 제3자에게 제공해서는 안 된다. 따라서 벤더의 독자적 광고 최적화가 허용되는지, 회사 목적의 수탁 처리인지 별도 목적 처리인지 계약과 실제 흐름으로 확인해야 한다.  
**[공식 원문 기반 제공 스냅샷] [UNVERIFIED: 기준일 현행성 미확인]** — 개인정보 보호법 제26조 제1항·제4항~제6항, 시행일 2025-10-02인 제공 스냅샷 대조. 2026-09-08 현재 전체 법령·하위규정은 제공되지 않았다. [법령 페이지](https://www.law.go.kr/법령/개인정보보호법)

벤더 서버가 해외에 있거나 해외에서 개인정보를 조회·보관한다면 국외이전 해당 여부와 적법근거를 별도로 검토해야 한다. 제공 법령 스냅샷은 국외 제공·조회·처리위탁·보관을 국외이전에 포함하고 있다.  
**[공식 원문 기반 제공 스냅샷] [UNVERIFIED: 기준일 현행성 미확인]** — 개인정보 보호법 제28조의8 제1항~제6항. 국가, 이전 항목, 시기·방법, 수령자, 목적·보유기간 등 구체 사실이 없어 본 건 적용 여부는 판단할 수 없다.

## 4. 출시 전 필수 확인·조치

### A. 실제 데이터 흐름 검증

1. 철회 전후 테스트 계정을 만들어 다음 로그를 하나의 타임라인으로 연결한다.

   - 이용자의 철회 요청 시각
   - 앱 설정 반영 시각
   - 신규 SDK 호출 및 이벤트 생성 여부
   - 기존 서버 수신기의 이벤트 수신 여부
   - 새 벤더로의 전송 시도·성공·실패 여부
   - 벤더 suppression 적용 시각

2. 구매 이벤트의 필드 목록에서 계정 ID, 광고식별자, 기기 식별자, 이메일·전화번호 파생값, IP 등 개인과 연결될 수 있는 값을 확인한다.

3. 앱 설정을 꺼도 서버가 독립적으로 이벤트를 전달하는 경로가 있다면 철회 상태를 서버의 전송 판단에 반영한다.

4. 철회 이용자에게 대체 식별자, 디지털 지문 또는 새로운 매칭키를 생성하는 우회 경로가 없는지 확인한다.

### B. 벤더 확인서 보완

벤더에게 다음 내용을 서면으로 다시 확인받는다.

- suppression 대상 식별자의 종류와 값의 연결 기준
- 적용 대상 처리 목적: 광고 노출, 타기팅, 프로파일링, 최적화, 측정, 모델·알고리즘 개선 등
- 적용 시각과 이전 전송분 처리
- 신규 수집·사용 중지와 기존 데이터 삭제의 구분
- 파생 프로필·세그먼트·백업·재위탁자에 대한 적용 범위
- 부분 실패 확인 방법과 재처리 절차
- 설정 변경이나 SDK 재설치 때 재활성화되는지

“suppression 완료”라는 표현만으로 삭제 완료 또는 모든 목적의 처리 중단으로 기록하지 않는다.

### C. 계약·고지 검토

- 벤더가 수탁자인지, 독립적인 광고 목적을 갖는지 역할을 확정한다.
- 계약·DPA에서 처리 목적, 목적 외 이용 금지, 데이터 항목, 보유·파기, 재위탁, 감사·로그 제공, 철회 및 권리 요청 전달을 확인한다.
- 벤더의 독자적 광고 최적화가 허용되어 있다면 해당 목적의 적법근거와 이용자 고지가 별도로 확보되는지 검토한다.
- 벤더 서버·지원 인력·재수탁자의 해외 소재 및 접근 여부를 확인한다.
- 처리방침에서 SDK 명칭·종류, 수집 주체, 수집 정보, 이용 목적 및 통제 방법이 실제 흐름과 일치하는지 확인한다.

안내서의 계약·DPA 항목과 감사 사례는 권고·비교 예시다. 특정 감사 주기, 삭제기한 또는 양식을 법정 의무로 전환하지 않는다.  
**[공식 실무자료 발췌] [VERIFIED: 제공 발췌 대조]** — 개인정보보호위원회, 「생성형 인공지능(AI) 개발·활용을 위한 개인정보 처리 안내서」(2025.8), PDF 27~28·50쪽. [원문 게시 페이지](https://www.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS217&mCode=G010030000&nttId=11439)

## 5. 출시 후 조치

출시 후에는 고정된 법정 주기를 임의로 만들지 말고, 변경과 위험에 연동하여 다음을 수행한다.

- 초기 운영 구간에서 철회 전후 서버·벤더 로그를 표본 대조한다.
- 철회 후 광고 목적 이벤트가 발견되면 전송을 차단하고 영향받은 식별자·기간·목적을 확정한다.
- suppression 실패 또는 지연 사례를 재처리하고 벤더 확인 증적을 보관한다.
- SDK 버전, 서버 라우팅, 이벤트 스키마, 벤더 목적 또는 재수탁자가 변경될 때 다시 검토한다.
- 철회 설정이 앱 재설치, 로그인 변경, 기기 변경 또는 SDK 초기화로 풀리지 않는지 회귀 테스트한다.
- 실제 전송 사실이 확인된 경우 이를 곧바로 “유출”이라고 단정하지 말고, 승인된 처리인지와 위탁 범위·적법근거를 먼저 확인한다. 무단 유출 가능성이 확인되면 개인정보 보호법 제34조에 따른 통지·신고 쟁점을 별도 검토한다. 제공 자료만으로 구체 신고기한·기준은 확정할 수 없다.

## 6. 성능 계측과 광고 철회의 구분

현재 확인된 성능 계측은 다음 조건을 모두 충족하므로 광고 SDK와 분리하여 관리할 수 있다.

- 개인·계정·기기 식별자를 사용하지 않음
- 재식별할 수 없는 집계값만 처리
- 내부 시스템에서만 처리
- 외부 벤더 전송이나 외부 접근이 없음
- 광고 프로필 또는 개인정보와 연결하는 매칭키가 없음

이 전제가 유지된다면 광고 철회는 **맞춤형 광고 목적의 식별·행태정보 처리와 외부 전송을 통제하는 기능**이고, 성능 계측은 **개인을 식별하지 않는 내부 집계 처리**이므로 동일하게 중단할 필요가 있다고 볼 근거는 제공 자료에 없다.

다만 다음 중 하나라도 발생하면 별도 판단을 다시 해야 한다.

- 사용자·기기별 원시값을 장기간 축적
- 세션 ID 등이 다른 데이터와 연결
- 희소한 집계값으로 특정 이용자를 추론할 수 있음
- 광고 시스템과 공통 매칭키 사용
- 외부 벤더 전송 또는 원격 접근 추가
- 집계 데이터를 광고 타기팅·프로파일링에 재사용

제품 문구도 이를 구별해, “맞춤형 광고 끄기”를 “앱의 모든 데이터 처리가 중단된다”는 의미로 표현하지 않는 것이 적절하다. 예시는 다음과 같다.

> 맞춤형 광고를 끄면 광고 개인화를 위한 정보의 수집·이용 및 관련 벤더 전송이 중단됩니다. 서비스 안정성과 성능 확인을 위한 비식별 집계 통계는 개인이나 기기를 식별하지 않는 형태로 내부에서 계속 처리될 수 있습니다.

이 문안은 실제 서버·벤더 처리 검증이 완료된 후 사용해야 한다.
