# 광고 SDK 교체 개인정보 검토 메모(초안)

- 기준일: 2026년 9월 8일
- 대상: 앱팀·개인정보 담당자
- 검토 범위: 맞춤형 광고 철회, 구매 이벤트 전송, 신규 광고 벤더의 처리, 내부 성능 계측
- 자료 범위: 제공된 법령 스냅샷과 개인정보보호위원회 안내·정책 발췌에 한정

## 1. 잠정 결론

현재 화면과 SDK 설정만으로는 맞춤형 광고 철회가 전체 처리 경로에서 완료되었다고 판단하기 어렵다.

앱에서는 철회 표시와 신규 SDK의 광고 설정 비활성화가 확인됐지만, 서버의 기존 이벤트 수신기가 구매 이벤트를 새 벤더로 보낼 수 있고 실제 전송 로그가 확보되지 않았다. 벤더의 “suppression 적용 완료” 회신도 대상 식별자, 억제 목적, 적용 시각 및 기존 보유 데이터 처리 여부가 없어 검증 자료로 충분하지 않다.

따라서 출시 전에는 최소한 다음 두 상태를 분리해야 한다.

1. 맞춤형 광고를 끈 이용자의 신규 광고 목적 수집·전송·활용이 앱과 서버, 신규 벤더 전 구간에서 중단되는지
2. 철회 전에 적법하게 보유하던 데이터가 어떤 목적과 근거로 남고, 언제 삭제·익명화되는지

반대로 모든 이벤트와 모든 보존 데이터를 즉시 삭제해야 한다고도 제공 자료만으로 단정할 수 없다. 자료는 사후 거부 기능과 우회 식별 금지의 필요성을 뒷받침하지만, 철회 시 모든 목적의 모든 데이터를 일률적으로 즉시 삭제해야 한다는 규칙은 제시하지 않는다. 삭제 범위는 데이터별 처리 목적, 법적 근거, 계약상 역할, 보유기간을 구분하여 정해야 한다.

출시 판단은 다음과 같이 제안한다.

> 구매 이벤트가 철회 이용자에 대해서도 신규 벤더로 전달될 수 있는 경로가 남아 있으므로, 해당 경로의 차단 또는 광고 목적 미사용을 객관적으로 검증하기 전에는 “맞춤형 광고 철회가 완전히 적용된다”고 출시 승인하지 않는다. 단순 집계 성능 계측은 아래 조건을 유지하는 한 별도 처리로 관리한다.

## 2. 현재 증거로 가능한 판단

| 항목 | 현재 판단 | 상태 |
|---|---|---|
| 앱 화면 | 철회 완료 표시가 구현됨 | 제품 사실로 확인 |
| 신규 SDK | 맞춤형 광고 설정이 꺼짐 | 제품 사실로 확인 |
| 서버 전송 | 기존 수신기가 구매 이벤트를 새 벤더로 전송할 가능성이 남음 | 실제 로그 부재로 전송 여부 미확인 |
| 벤더 억제 | “suppression 적용 완료”라는 회신만 존재 | 대상·목적·시각이 없어 효과 범위 미확인 |
| 벤더 자체 최적화 | 계약상 허용 또는 금지 여부 불명 | 계약 확인 필요 |
| 성능 계측 | 개인·기기 식별자 없이 재식별할 수 없는 집계값만 내부 처리하고 외부 전송하지 않음 | 제공된 사실관계에서 광고 처리와 구별 가능 |

온라인 식별자나 행태정보가 회원정보 등과 결합되어 개인을 식별할 수 있다면 개인정보에 해당할 수 있다. 랜덤 식별자도 누적·중첩·결합을 통해 개인 식별 가능성이 생기면 같은 위험이 있다. 반면 합리적으로 고려할 때 다른 정보와 쉽게 결합하여 개인을 알아볼 수 없다면 개인정보로 보지 않을 수 있다는 것이 제공 정책자료의 판단 구조다.

**[공식 실무자료] [VERIFIED]** — 개인정보보호위원회 「맞춤형 광고에 활용되는 온라인 행태정보 보호를 위한 정책 방안」(2024.1) PDF 22쪽 원문 발췌 확인. 2026-09-08 확보한 선택 페이지 기준이며, 현재 법령 전체를 공식 사이트에서 재확인한 것은 아님.  
Supports: 식별자 명칭보다 결합·누적 가능성과 실제 식별 가능성을 중심으로 판단해야 한다는 점.

개인을 식별하여 처리하는 맞춤형 광고에는 적법한 수집 요건과 사후 거부 기능이 요구된다는 것이 정책자료의 설명이다. 또한 거부한 이용자를 다른 식별자나 디지털 지문으로 다시 추적하여 차단을 우회해서는 안 된다고 한다.

**[공식 실무자료] [VERIFIED]** — 같은 정책 방안 PDF 25~26쪽 원문 발췌 확인. 일부 내용은 문서 자체에서 “권고”로 표시되어 있으므로 모두 법적 의무로 취급하지 않음.  
Supports: 화면 버튼뿐 아니라 실제 광고 목적 처리가 중단되고 우회 식별이 없어야 한다는 검토 방향.

## 3. 화면과 회신만으로 부족한 이유

철회의 실효성은 최소한 다음 경로 전체에서 확인되어야 한다.

`이용자 설정 → 앱 SDK → 서버 이벤트 라우팅 → 신규 벤더 수신 → 벤더 내부 광고 최적화·프로파일링`

현재는 앞의 두 단계만 확인됐다. 서버가 구매 이벤트를 계속 전달하면 다음 가능성이 남는다.

- SDK의 맞춤형 광고 플래그와 무관하게 서버 측 이벤트가 전달되는 경우
- 벤더가 suppression을 광고 노출에만 적용하고 프로파일링이나 모델 최적화에는 계속 사용하는 경우
- suppression 대상 식별자가 앱 계정, 광고식별자 또는 서버 고객키 중 일부에만 적용된 경우
- 철회 이후 신규 전송은 막았지만 철회 전에 보유한 프로필에는 적용하지 않은 경우

이는 현재 사실로 확정된 문제가 아니라, 확보되지 않은 증거 때문에 배제할 수 없는 시나리오다.

벤더가 수탁자라면 위탁 문서에는 위탁 목적 외 처리 금지와 보호조치가 포함되어야 하고, 위탁자는 처리 현황 점검 등을 통해 수탁자를 감독해야 한다. 수탁자는 위탁받은 범위를 초과하여 이용하거나 제3자에게 제공할 수 없다.

**[공식 원문 기반 로컬 스냅샷] [VERIFIED]** — 개인정보 보호법(법률 제20897호, 2025-10-02 시행본) 제26조 제1항·제4항·제5항 원문 발췌 확인. 직접 law.go.kr을 연 것은 아니며 2026-09-08 현재 미제공 개정 내용은 확인 불가.  
Supports: 수탁자 구조라면 목적 제한을 계약에 명시하고 실제 처리 현황을 감독해야 한다는 판단.

다만 벤더가 구매 이벤트를 독자적인 광고 최적화에 사용하는 경우 그것이 위탁 범위인지, 별도의 제3자 제공 또는 벤더의 독자적 처리가 되는지는 제공 자료와 현재 계약 정보만으로 확정할 수 없다. 계약과 실제 데이터 흐름을 함께 확인해야 한다.

## 4. 출시 전 필수 확인·조치

### 앱팀

- 철회 전후 테스트 계정을 만들어 앱 SDK 요청과 서버 발신을 함께 추적한다.
- 맞춤형 광고 철회 이용자의 구매 이벤트가 신규 벤더 목적지로 라우팅되는지 확인한다.
- 전송이 계속 필요하다고 주장되는 이벤트는 광고, 결제 운영, 부정거래 방지 등 목적별로 분리한다. “분석”처럼 포괄적인 목적명만 사용하지 않는다.
- 광고 목적 전송에는 철회 상태가 서버에서도 강제되도록 한다. 클라이언트 설정만 신뢰하지 않는다.
- 계정 ID, 광고식별자, 해시 이메일, 주문번호, 벤더 ID 등 우회 결합 가능한 키가 남는지 점검한다.
- 철회 UI는 실제 백엔드 적용 성공 여부와 연결한다. 백엔드 적용 실패 상태에서 “철회 완료”로 확정 표시하지 않도록 오류 처리와 재시도 정책을 둔다.

### 개인정보 담당자

벤더에게 다음 내용을 보완 요청한다.

- suppression 대상 식별자의 정확한 종류
- 적용 대상 데이터셋과 처리 목적
- 적용 시각 및 적용 전후의 이벤트 수신 여부
- 신규 수집·프로파일 갱신·광고 노출·모델 최적화 중 각각 무엇이 중단되는지
- 기존 프로필·원시 이벤트·파생 세그먼트의 보유 및 삭제·익명화 정책
- 재위탁자 및 국외 처리·보관 위치
- 검증 가능한 처리 로그나 관리자 보고서
- 철회 신호가 누락되거나 지연될 때의 처리 방식

계약과 DPA에서는 다음을 확인하거나 보완한다.

- 벤더가 회사 지시에 따라 처리하는 수탁자인지
- 독자적인 광고 최적화, 상품 개선 또는 교차고객 학습이 허용되는지
- 목적 외 이용 및 재이용 제한
- 철회 신호의 적용 범위와 처리 기한
- 삭제·반환·익명화 기준과 증빙
- 재위탁 통제와 감사·점검권
- 국외 이전의 국가, 수령자, 목적, 보유기간 및 적용 근거

개인정보의 국외 제공·처리위탁·보관이 있다면 개인정보 보호법 제28조의8에 따른 허용 근거와 관련 고지·보호조치를 별도로 검토해야 한다.

**[공식 원문 기반 로컬 스냅샷] [VERIFIED]** — 개인정보 보호법 제28조의8 제1항·제2항·제4항·제5항 원문 발췌 확인. 2025-10-02 시행본이며 직접 공식 사이트 확인은 아님.  
Supports: 국외 처리 여부를 계약과 실제 데이터 흐름에서 별도로 확인해야 한다는 판단.

## 5. 데이터 삭제 범위

현재 단계에서는 “전부 즉시 삭제”와 “아무것도 삭제하지 않음” 모두 근거가 부족하다. 다음 표처럼 목적별로 정리하는 것이 안전하다.

| 데이터 범주 | 철회 후 잠정 처리 |
|---|---|
| 신규 맞춤형 광고용 이벤트·프로필 갱신 | 중단 여부를 출시 전에 검증 |
| 철회 이용자를 다시 식별하기 위한 대체 식별자·디지털 지문 | 생성하거나 조합하지 않음 |
| 기존 광고 프로필·세그먼트 | 벤더 suppression 범위와 보유 목적 확인 후 삭제·비활성화·익명화 결정 |
| 구매 이행에 필요한 거래기록 | 광고 철회와 별도 목적·근거·보유기간 검토 |
| 보안·부정거래 방지 데이터 | 광고 목적 사용과 분리하여 별도 근거 검토 |
| 비식별 내부 성능 집계값 | 아래 조건을 유지하면 광고 철회 대상과 분리 가능 |

AI 안내서는 옵트아웃 이후 데이터 수집 중지, 수집·거부·파기 정책의 투명한 공개, 이용자가 입력한 데이터의 제거 기능 등을 권리보장 강화 사례로 제시한다. 그러나 이는 생성형 AI 맥락의 공식 안내 사례이므로 광고 SDK에 그대로 적용되는 법정 삭제 규칙으로 볼 수 없다.

**[공식 실무자료] [VERIFIED]** — 개인정보보호위원회 「생성형 인공지능 개발·활용을 위한 개인정보 처리 안내서」(2025.8) PDF 46쪽 원문 발췌 확인. 광고 SDK에 대해서는 설계 참고자료로만 사용.  
Supports: 철회 이후 신규 수집 중지와 보유 데이터 정책을 구분해 투명하게 정할 필요성.

## 6. 광고 철회와 내부 성능 계측의 구별

광고 철회는 “광고와 관계된 모든 기술 처리를 중단한다”는 의미로 넓히기보다, 다음 네 축으로 구분해야 한다.

| 구분 | 맞춤형 광고 처리 | 확인된 성능 계측 |
|---|---|---|
| 목적 | 이용자별 광고 선택·최적화 | 앱 성능의 집계 측정 |
| 데이터 | 구매 이벤트, 온라인 식별자, 프로필과 결합 가능 | 개인·기기 식별자 없는 재식별 불가능 집계값 |
| 처리 위치 | SDK·서버·외부 벤더 가능 | 내부 시스템만 사용 |
| 외부 제공 | 신규 벤더 전송 가능성이 남음 | 외부 전송 없음 |
| 철회 효과 | 신규 광고 목적 수집·전송·활용을 중단해야 하는 대상 | 확인된 구조가 유지된다면 자동 중단 대상이라고 보기 어려움 |

따라서 광고 철회 시 내부 성능 집계까지 자동 삭제하거나 중단해야 한다고 볼 근거는 제공 자료에 없다. 다만 이 구별은 다음 조건이 계속 충족될 때만 유지된다.

- 집계 전 원시 데이터에 개인·기기 식별자가 붙지 않을 것
- 광고·회원 시스템과 결합할 매칭키가 없을 것
- 소규모 집계나 세분화로 개인을 추론할 수 없을 것
- 외부 벤더로 전달되지 않을 것
- 광고 최적화나 이용자 프로파일링에 재사용되지 않을 것

## 7. 출시 후 관리

- 첫 운영 구간에서 철회 계정의 앱 요청, 서버 발신 및 벤더 수신 결과를 표본 대조한다.
- SDK 버전이나 서버 라우팅 규칙이 바뀌면 철회 경로 회귀 테스트를 수행한다.
- 벤더가 suppression 정의, 자체 목적 또는 재위탁자를 변경하면 계약·처리방침 영향을 재검토한다.
- 광고 수집도구의 명칭, 수집 주체, 수집 정보, 목적 및 통제방법이 이용자 안내와 일치하는지 확인한다.
- 성능 계측은 광고 데이터와의 결합키 생성, 외부 전송 또는 세분화 수준 변화가 생길 때 다시 분류한다.
- 점검 결과는 테스트 계정, 시각, 이벤트 종류, 발신·수신 결과와 벤더 확인 내용을 남긴다.

위 조치는 위험 기반 운영안이다. 제공 안내서의 “주기적 점검”, “재고지”, “감사” 사례를 고정된 법정 점검 주기나 필수 양식으로 해석하지 않는다. 구체적인 법정 기한·필수 서식·하위규정 요건은 제공 자료에 없어 이 메모에서 확정하지 않는다.
