# SDK 교체 검토 메모(초안)

- 기준일: 2026년 9월 8일
- 대상: 앱팀·개인정보 담당자
- 범위: 광고 SDK 교체, 맞춤형 광고 철회 전파, 서버 이벤트 전달, 성능 계측
- 검토 한계: 제공된 법령 스냅샷과 공식 안내자료의 선택 페이지에만 근거하였다. 현행 법령 전체·시행령·고시·벤더 계약 및 실제 로그는 확인하지 못했으므로 아래 법률 평가는 잠정적이다.

## 1. 검토 결론

현재 증거만으로는 “맞춤형 광고 철회가 신규 SDK와 서버 전달 경로 및 벤더 측 처리까지 완료되었다”고 판단하기 어렵다.

화면의 철회 완료 표시와 신규 SDK의 광고 설정 비활성화는 클라이언트 단계의 작동 증거가 될 수 있다. 그러나 서버의 기존 이벤트 수신기가 구매 이벤트를 새 벤더로 보낼 수 있고 실제 전송 로그가 제출되지 않았으므로, 서버 측 전달 차단 여부는 확인되지 않았다. 벤더 회신도 대상 식별자·처리 목적·적용 시각을 밝히지 않아 해당 사용자의 어떤 처리가 언제부터 억제되었는지 검증할 수 없다.

따라서 권고 결론은 다음과 같다.

- 광고 관련 서버 전송 경로는 아래 출시 전 조건이 충족될 때까지 운영 승인을 보류하거나, 기술적으로 비활성화한 상태에서 출시한다.
- 성능 계측은 현재 확인된 구조, 즉 개인·기기 식별자가 없고 재식별할 수 없는 집계값만 내부에서 처리하며 외부 전송도 없다는 조건이 유지된다면 광고 철회와 별개의 처리로 구분할 수 있다.
- 모든 이벤트와 모든 보존 데이터를 일률적으로 즉시 삭제해야 한다는 결론도 제공 자료만으로는 성립하지 않는다. 광고 목적 데이터, 서비스 운영 데이터, 재식별 불가능한 집계값을 분리하고 각 데이터의 처리 목적·식별 가능성·보유 필요성을 개별 판단해야 한다.

## 2. 현재 증거로 가능한 판단

| 항목 | 잠정 판단 | 근거와 상태 |
|---|---|---|
| 앱 화면의 철회 표시 | 사용자가 철회 조작을 완료했다는 UI 증거는 있음 | 다만 후속 서버·벤더 처리까지 입증하지는 않음 |
| 신규 SDK 광고 설정 | 클라이언트 SDK의 맞춤형 광고 설정은 꺼진 것으로 확인됨 | 서버의 기존 이벤트 전달 가능성과 별도 경로임 |
| 구매 이벤트의 실제 외부 전송 | 확인 불가 | 서버가 전달할 수 있으나 실제 송수신 로그가 없음 |
| 벤더 suppression | 적용 범위 확인 불가 | 대상 식별자·목적·적용 시각이 빠진 회신만으로는 광고 최적화, 프로파일링, 하위 파트너 처리가 모두 중단되었는지 알 수 없음 |
| 벤더의 독자적 광고 최적화 | 확인 불가 | 계약·DPA·상품 정책이 제공되지 않음 |
| 성능 계측 | 제시된 사실이 유지되는 한 광고 개인정보 처리와 구분 가능 | 개인·기기 식별자 부재, 재식별 불가능한 집계값, 내부 처리, 외부 전송 없음이 전제 |

온라인 식별자나 행태정보가 회원정보 등과 결합되거나 누적·중첩·결합을 통해 개인을 식별할 수 있다면 개인정보에 해당할 가능성이 높다. 반대로 개인정보가 포함되지 않고 다른 정보와 쉽게 결합해 개인을 알아볼 수 없는 행태정보는 개인정보로 보지 않을 수 있다. **[공식 실무자료 발췌] [UNVERIFIED]** — 「맞춤형 광고에 활용되는 온라인 행태정보 보호를 위한 정책 방안」 PDF 22쪽. 2026-09-08 확보본의 선택 페이지를 확인했으며, 현행 법령 전체를 직접 확인한 것은 아니다.

또한 맞춤형 광고 거부 후 다른 온라인 식별자나 디지털 지문을 만들어 차단을 우회해서는 안 된다고 안내한다. **[공식 실무자료 발췌] [UNVERIFIED]** — 같은 정책 방안 PDF 26쪽. 이 자료의 투명성·사후 통제권 관련 일부 내용은 권고사항이므로 개별 항목을 모두 법적 의무로 취급하지 않는다.

## 3. 핵심 쟁점

### 3.1 화면과 벤더 회신만으로 충분한가

충분하지 않다.

철회 완료 여부는 적어도 다음 경로를 연결해 확인해야 한다.

```text
사용자 철회
→ 앱·신규 SDK 설정 변경
→ 서버 이벤트 전달 규칙 반영
→ 새 벤더 수신 또는 차단
→ 벤더의 광고 목적 처리 및 하위 전달 억제
```

현재는 첫 두 단계만 확인됐다. 구매 이벤트가 서버에서 새 벤더로 전달되지 않았다는 증거와, 벤더가 어떤 식별자·목적·시점에 suppression을 적용했는지가 빠져 있다.

벤더가 수탁자라면 위탁 목적 외 처리가 금지되고, 위탁자는 처리 현황 점검 등을 통해 수탁자를 감독해야 한다. **[공식 원문 기반 법령 스냅샷] [UNVERIFIED]** — 개인정보 보호법 제26조 제4항·제5항, 시행 2025-10-02 스냅샷 확인. 2026-09-08 현재 법령과 하위규정은 직접 확인하지 못했다.

### 3.2 모든 이벤트와 보존 데이터를 즉시 삭제해야 하는가

제공 자료는 광고 철회 시 모든 이벤트와 모든 보존 데이터를 일률적으로 즉시 삭제해야 한다는 규칙을 확립하지 않는다.

다음과 같이 분리해야 한다.

- 광고 맞춤화·프로파일링을 위한 수집과 신규 전송
- 이미 벤더에 전달된 광고 목적 데이터
- 법적·계약상 근거가 확인된 별도 목적 데이터
- 개인·기기와 연결되지 않는 내부 집계 성능지표
- 백업이나 기술적 잔존 데이터

AI 안내서에는 옵트아웃 이후 학습데이터 수집 중지, 손쉬운 삭제 기능, 계약상 재이용 제한과 데이터 파기 조건을 명확히 하라는 사례·권고가 있다. 그러나 이는 생성형 AI 맥락의 예시이므로 광고 SDK에 대한 고정된 삭제 의무나 기한으로 그대로 적용할 수 없다. **[공식 실무자료·유추 참고] [EDITORIAL]** — 「생성형 인공지능 개발·활용을 위한 개인정보 처리 안내서」 PDF 27~28쪽, 46쪽.

따라서 광고 목적의 신규 수집·전송은 철회 상태에 맞춰 중단하되, 기존 데이터 삭제 범위와 시점은 데이터 항목, 처리 목적, 식별 가능성, 벤더 계약, 보유 근거를 확인한 뒤 정해야 한다.

### 3.3 벤더의 독자적 광고 최적화 가능성

현재 계약이 없으므로 판단을 유보한다.

벤더가 회사의 지시에 따라 광고 업무만 수행하는지, 아니면 수신한 구매 이벤트를 자체 모델 개선·광고 최적화·다른 고객 대상 서비스에 사용하는지가 핵심이다. 독자적 목적 사용 여부가 확인되지 않으면 위탁인지 다른 제공 구조인지도 확정하기 어렵다.

개인정보 수탁자는 위탁 범위를 초과해 개인정보를 이용하거나 제3자에게 제공할 수 없다. **[공식 원문 기반 법령 스냅샷] [UNVERIFIED]** — 개인정보 보호법 제26조 제5항. 현재성 및 구체적인 구조 분류는 추가 확인이 필요하다.

## 4. 출시 전 필수 확인 및 조치

| 담당 | 조치 | 완료 증거 |
|---|---|---|
| 앱팀 | 맞춤형 광고를 끈 계정·기기에서 신규 SDK 광고 이벤트가 생성되지 않는지 테스트 | 앱·SDK 버전, 테스트 시각, 철회 전후 이벤트 및 payload 비교 |
| 서버팀 | 철회 상태가 기존 이벤트 수신기의 forwarding rule에 반영되는지 확인 | 규칙 ID·버전, 대상 이벤트, 목적지 벤더, 철회 전후 송신 로그 |
| 서버팀 | 구매 이벤트가 서비스 필수 분석과 광고 전달 중 어느 경로로 사용되는지 분리 | 이벤트명, 필드, 식별자, 처리 목적, 목적지 매핑표 |
| 개인정보 담당자 | 벤더에 suppression 범위 보완 요청 | 요청 ID, 대상 식별자·가명키, 처리 목적, 적용 시각, SDK 버전, 하위 파트너 적용 범위, 예외·실패 여부가 포함된 회신 |
| 법무·개인정보 담당자 | 계약·DPA·벤더 정책에서 독자적 광고 최적화와 재이용 여부 확인 | 목적 외 이용 금지, 재위탁, 보유·삭제, 감사·증적 제공 조항 |
| 개인정보 담당자 | 처리방침과 앱 내 안내가 신규 SDK 및 실제 데이터 흐름과 일치하는지 확인 | 수집도구명, 수신자, 항목, 목적, 통제방법, 변경 반영일 |
| 출시 책임자 | 위 증거가 없으면 광고 서버 forwarding을 기본 차단 | 배포 설정 및 차단 테스트 결과 |

행태정보 수집도구를 통한 제3자 수집은 수집도구 명칭·종류, 수집자, 정보 내용, 이용 목적, 통제방법 등을 웹·앱별 처리방침에 공개하도록 권고된다. CPO의 수집도구 현황 파악과 점검도 권고되지만, 제공 자료는 특정한 법정 점검 주기나 필수 양식을 정하지 않는다. **[공식 실무자료 발췌] [UNVERIFIED]** — 행태정보 정책 방안 PDF 29~30쪽.

## 5. 출시 후 조치

출시 후에는 고정된 형식이나 획일적 주기보다 변경·위험에 연동하여 확인한다.

- 최초 운영 구간에서 철회 계정의 광고 이벤트가 앱, 서버, 벤더 어느 단계에도 남지 않는지 표본 검증한다.
- SDK, 서버 container, forwarding rule, 목적지 벤더, payload 또는 동의 신호 매핑이 변경될 때 재검증한다.
- 벤더의 suppression 실패나 예외 회신을 기록하고 재처리 결과까지 연결한다.
- 벤더·서브프로세서 변경 시 계약, 처리방침, 벤더 목록과 실제 전송 구성을 함께 갱신한다.
- 광고 철회 후에도 구매 이벤트가 전송된 정황이 발견되면 즉시 해당 경로를 차단하고, 영향 범위·식별자·수신자·처리 목적을 조사한다. 다만 제공 자료만으로 이를 곧바로 법 제34조상 유출로 단정할 수는 없다.
- 성능 계측에는 식별자나 원시 이벤트가 새로 추가되거나 외부 전송이 생기는지를 변경 시점마다 확인한다.

## 6. 광고 철회와 성능 계측의 구별

광고 철회는 맞춤형 광고를 위한 개인·기기 단위의 수집, 프로파일링, 식별자 생성 및 벤더 전달을 통제하는 문제다. 철회 후에는 광고 설정만 꺼지는 것이 아니라, 서버 전달과 벤더 목적 처리까지 철회 상태가 전파되는지 확인해야 한다.

반면 현재 성능 계측은 다음 조건 때문에 별도 취급할 수 있다.

- 개인 또는 기기 식별자가 없다.
- 재식별할 수 없는 집계값만 처리한다.
- 내부 시스템에서만 처리한다.
- 외부 벤더로 전송하지 않는다.
- 광고 대상 선정이나 개인별 프로파일링에 사용하지 않는다.

따라서 맞춤형 광고 철회를 이유로 이 집계 계측까지 자동 삭제하거나 중단해야 한다고 볼 근거는 제공 자료에 없다. 다만 집계 단위가 지나치게 작아 개인을 추론할 수 있게 되거나, 원시 이벤트·식별자·외부 전송이 추가되면 이 구분은 다시 검토해야 한다.

## 7. 잠정 출시 판단 문안

> 신규 SDK의 클라이언트 광고 설정 비활성화는 확인되었으나, 서버 구매 이벤트의 전달 차단과 벤더 suppression의 대상·목적·적용 시각은 확인되지 않았다. 따라서 광고 관련 서버 전달은 차단 상태로 출시하거나 관련 로그와 벤더 보완 확인서를 확보한 후 활성화한다.  
>  
> 개인·기기 식별자 없이 재식별 불가능한 집계값만 내부 처리하는 성능 계측은 광고 철회와 구분하여 유지할 수 있다. 다만 식별자, 원시 이벤트 또는 외부 전송이 추가되는 변경 시 재검토한다.  
>  
> 모든 기존 데이터를 일괄 즉시 삭제하지는 않되, 광고 목적 데이터는 신규 수집·전송 중단 여부를 우선 확인하고 기존 보유분은 항목별 목적·식별 가능성·보유 근거·벤더 처리 범위를 확인하여 삭제 또는 제한 여부를 결정한다.
