# SDK 교체 검토 메모 (내부용)

**대상:** 앱팀, 개인정보 담당자  
**건:** 커머스 앱 광고 SDK 교체 — 맞춤형 광고 철회가 실제 처리 중단인지  
**기준일:** 2026-09-08  
**성격:** 출시 전 내부 검토 초안. 송부·서명·대외 회신 문안이 아님.

사용 범위: 아래 판단은 **제공된 고정 발췌**만으로 적는다. 법령은 시행 2025-10-02·법률 20897호 스냅샷이고, 안내서·정책방안은 해당 PDF 발췌다. 지금 공식 사이트를 연 확인이 아니다. 발췌에 없는 조문·하위규정·계약 문구·전송 로그는 추정하지 않는다.

---

## 1. 지금 증거로 말할 수 있는 것

화면의 “철회 완료”와 신규 SDK 광고 설정 off, 벤더의 “suppression 적용 완료” 회신만으로는 **맞춤형 광고 목적 처리가 모든 경로에서 멈췄다고 볼 수 없다.** 반대로, 그 공백을 메우려고 **모든 이벤트와 모든 보존 데이터를 즉시 삭제해야 한다는 법정 의무도 이번 자료만으로는 세워지지 않는다.**

현재 사실과 그에 붙는 판단은 다음뿐이다.

| 확인된 사실 | 지금 붙일 수 있는 판단 | 상태 |
|---|---|---|
| 이용자가 맞춤형 광고를 끄면 화면에 철회 완료가 표시되고, 신규 SDK 광고 설정도 꺼진다 | 이용자 접점과 **클라이언트 SDK 설정**이 꺼진 것은 맞다. 서버 전송·벤더 측 처리·과거 보존 데이터까지 멈춘 증거는 아니다 | 제품 사실 |
| 서버의 기존 이벤트 수신기는 구매 이벤트를 새 벤더로 **보낼 수 있다**. 이번 점검은 **실제 전송 로그를 받지 못했다** | “보낼 수 있는 경로”가 남아 있다는 점과, 철회 이후 **실제로 보냈는지**는 별개다. 로그 부재를 미전송으로 읽지 않는다 | 경로 존재 / 전송 여부 `[INSUFFICIENT]` |
| 벤더는 suppression 적용 완료라고만 했고, **대상 식별자·목적·적용 시각**은 적지 않았다 | 회신은 접수 사실일 뿐, 어떤 식별자에 대해 어떤 목적의 처리를 언제부터 멈췄는지는 미확인이다. `opt-out` / `suppression` / `delete`를 같은 말로 취급하지 않는다 | 회신만 확인 |
| 계약상 벤더의 **독자 광고 최적화** 허용 여부는 확인되지 않았다 | 위탁이라면 수탁자는 위탁 범위를 초과해 이용할 수 없다. 다만 이 관계가 위탁인지, 구매 이벤트가 개인정보인지는 이번 자료·계약으로 확정되지 않았다 | 계약·관계 `[INSUFFICIENT]` |
| 성능 계측은 개인·기기 식별자 없이 재식별 불가능한 집계만 내부 처리하고, 외부 벤더 전송이 없다 | 광고 철회 쟁점과 **다른 처리**다. 이 전제가 유지되는 한, 광고 SDK의 동의·suppression·국외이전 쟁점을 이 계측에 자동으로 옮기지 않는다 | 확인된 제품 사실 |

제품팀의 “화면과 회신이면 충분하다”는 지금 증거 수준을 넘는다. 다른 담당자의 “전부 즉시 삭제”도, 제공 법령 발췌에 **파기 조문이 없고**, 정책·안내서의 권고·예시를 그 내용으로 읽을 수 없다.

## 2. 광고 철회와 성능 계측을 구별하는 기준

맞춤형 광고 SDK와 내부 성능 계측은 목적, 식별 가능성, 외부 전송이 다르다. 철회 UI가 켜졌다고 후자까지 멈추라는 결론, 또는 후자가 안전하니 전자의 서버 경로도 문제 없다는 결론 모두 이 사실관계와 맞지 않는다.

**광고 SDK 쪽 (아직 개인정보 해당 여부를 단정하지 않음)**  
정책방안은 행태정보를 이용자 식별자와 결합하면 개인정보에 해당할 수 있고, 식별하여 처리하면 동의 등 적법 요건과 사후 거부 기능이 필요하다고 본다. 식별하지 않고 처리하려면 개인정보와의 결합이 발생하지 않게 해야 하며, 거부한 기기·웹·앱에 대해 다른 방식으로 맞춤형 광고용 온라인 식별자를 만드는 것은 막아야 한다고 적는다. 다만 후자(우회 식별자 생성 금지, 투명성, 사후 거부 UI)는 이 문서에서 **권고 또는 식별하지 않는 처리의 조건**으로 적혀 있고, 제15조·제22조·제37조 본문이 모두 이번 법령 발췌에 있는 것은 아니다. 제15조 본문만 법령 스냅샷에 있다.

이 건에서 아직 모르는 것은 구매 이벤트에 어떤 식별자가 붙는지, 철회 이후에도 새 벤더로 나가는지, 벤더가 그 데이터로 맞춤형 광고·독자 최적화를 하는지다. 화면 off만으로 이 축을 닫지 않는다.

**성능 계측 쪽 (이번 점검에서 전제가 확인됨)**  
정책방안 사례 ③은, 식별자를 랜덤하게 구성하고 행태정보에 개인정보가 없으며 합리적으로 볼 때 다른 정보와 쉽게 결합해 특정 개인을 알아볼 수 없으면 개인정보로 볼 수 없다고 한다. 이번 계측은 그보다 더 좁다. **식별자 자체가 없고**, 재식별 불가능한 집계만 내부에서 처리하며 **외부 전송이 없다.** 이 전제가 유지되면 광고 동의, 벤더 suppression, 국외이전을 이 계측에 붙여 쟁점화하지 않는다.

실무적으로는 두 파이프라인을 설정·로그·계약에서 섞지 않으면 된다. 광고 식별자·구매 이벤트가 성능 집계 키로 쓰이거나, 집계 시스템이 벤더로 포워딩되기 시작하면 이 구별은 다시 열린다.

## 3. 두 입장에 대한 검토

### 화면·벤더 회신만으로 충분한가

충분하지 않다.

철회는 이용자 접점의 표시가 아니라, 그 의사에 맞춰 **실제 처리가 어디서 멈추는가**의 문제다. 이번 점검만으로 확인된 중단은 화면과 신규 SDK 광고 설정뿐이다. 남아 있는 서버 수신기가 구매 이벤트를 새 벤더로 보낼 수 있고, 그 실제 전송 여부는 로그가 없다. 벤더 회신은 대상·목적·시각이 비어 있어, 광고 설정 off와 suppression이 같은 범위인지도 대조할 수 없다.

법령 스냅샷상 위탁이면 문서로 목적 외 처리를 금하고, 수탁자는 위탁 범위를 초과해 이용할 수 없다. 홍보·판매 권유 위탁이면 위탁 업무와 수탁자를 알릴 의무도 있다. 이 조문들이 지금 바로 “출시 불가”를 말하는 것은 아니다. 다만 **위탁 여부와 벤더 독자 최적화가 미확인인 상태에서, 화면과 회신을 준수 증거로 쓰는 것은 이르다.**

### 모든 이벤트·모든 보존 데이터를 즉시 삭제해야 하는가

이번 자료만으로는 그 결론을 내릴 수 없다.

- 제공된 법령 발췌에 **보유기간·파기 조문이 없다.** 즉시 전부 삭제를 현행 의무로 쓰지 않는다.
- 생성형 AI 안내서의 opt-out 예시는 “opt-out 설정 **이후부터** 데이터 수집 중지”를 보유·파기 안내의 예로 든다. 과거 raw·파생 데이터 일괄 삭제나, 광고 SDK의 법정 파기 양식이 아니다. 이 건은 서비스형 LLM·학습 재이용 축이 열려 있지 않다.
- 정책방안의 사후 통제는 맞춤형 광고 거부 및 우회 식별자 생성을 다루는 쪽이지, “모든 보존 데이터의 즉시 삭제”를 적시하지 않는다.

지금 할 일은 전부 삭제가 아니라, **철회 이후에도 광고 목적 처리가 남는 경로가 있는지**를 식별자·목적·시점 단위로 닫는 것이다. 그 확인 결과 개인정보가 광고 목적으로 계속 쓰이면, 그때의 조치(처리 정지, 목적 외 이용 차단, 필요 범위의 삭제)는 확인된 범위에 맞춰 다시 적는다.

## 4. 남은 확인 (이 칸이 채워지기 전에는 준수·미준수를 쓰지 않음)

1. **철회 UI가 실제로 끊는 범위**  
   클라이언트 광고 설정만인지, 서버 이벤트 포워딩·벤더 측 프로파일·리타게팅 포함인지.

2. **서버 → 새 벤더 구매 이벤트**  
   철회 전후 전송 로그. 포함 항목(광고식별자, 회원키, 주문번호 등), 철회 이용자에 대한 송신 여부, 실패·재시도.

3. **벤더 suppression의 내용**  
   대상 식별자, 적용 목적(맞춤형 광고 / 측정 / 벤더 독자 최적화), 적용 시각, 부분 실패, 재활성화 조건. “적용 완료” 문장만으로는 부족하다.

4. **계약·처리 관계**  
   위탁인지 제공인지, 목적 외·독자 광고 최적화 허용 여부, 재위탁, 삭제·처리정지 요청의 전파. 제26조를 적용하려면 이 관계가 먼저다. 제3자 제공 조문은 이번 법령 발췌에 없다.

5. **구매 이벤트·SDK 식별자의 개인정보 해당 여부**  
   회원정보·이메일·전화번호 등과 결합되는지, 아니면 결합 키 없이 운영되는지. 정책방안 사례 ①·②와 ③의 갈림이다. 지금은 광고 SDK 쪽에 사례 ③을 가정하지 않는다.

6. **국외이전**  
   벤더 서버 위치·조회 포함 이전 여부는 이번 사실에 없다. 제28조의8 적용을 열거나 닫지 않는다.

7. **성능 계측 전제의 유지**  
   식별자 없는 내부 집계, 외부 미전송이 코드·설정에서 계속 맞는지. 맞으면 광고 철회 조치 대상이 아니다.

## 5. 출시 전후 조치

아래는 **이 건의 확인 공백을 메우기 위한 실무 순서**다. 안내서 체크리스트나 정책방안의 권고를 법정 점검 주기·필수 서식으로 바꾼 것이 아니다. “분기 1회 감사”, “연 1회 재고지”, “DPA 필수 양식”처럼 읽지 않는다.

### 출시 전

- 철회 이용자 계정·기기로 **구매 이벤트가 새 벤더에 나가지 않는지** 로그로 확인한다. 경로가 남아 있으면 SDK 설정 off와 별도로 서버 포워딩을 끈다.
- 벤더에 suppression의 **식별자·목적·시각**을 회신으로 남긴다. 비어 있으면 “적용 완료”를 근거 목록에서 뺀다.
- 계약에서 벤더 독자 최적화가 허용되는지 확인한다. 허용 여부가 비어 있고 구매 이벤트가 개인정보에 해당하면, 위탁 목적 외 처리 위험이 열린 채로 출시하는 셈이다.
- 처리방침에 수집도구·제3자·목적·통제 방법을 어떻게 쓸지는 정책방안상 **권고**다. 공개 여부와 문구는 법무·개인정보 담당이 이번 확인 결과에 맞춰 정한다. 권고를 출시 차단 조건으로 자동 승격하지 않는다.
- 성능 계측은 광고 SDK 변경 범위에서 제외하되, 식별자·외부 전송이 생기지 않는지만 한 번 더 본다.

### 출시 직후

- 철회 이용자에게 광고 목적 식별자가 다시 만들어지거나, 다른 키로 구매 이벤트가 붙는지 본다. 정책방안이 금지로 적은 것은 “거부 후 다른 방식으로 맞춤형 광고용 식별자를 생성하는 것”이다. 이를 특정 로그 항목이나 suppression SLA로 바꾸지 않는다.
- 벤더 회신의 적용 시각 이후 구간에서 송신 로그를 대조한다. 부분 실패가 있으면 그 범위만 적고, 전체 중단으로 올리지 않는다.

### 출시 이후 운영

- 웹·앱에 설치된 행태정보 수집도구의 현황 파악은 정책방안이 CPO 관리책임의 **권고**로 적는다. 주기 숫자나 고정 서식을 법령 의무로 만들지 않는다. 도구가 늘거나 벤더가 바뀌면 그때 제26조 공개·홍보 위탁 고지 해당 여부만 다시 보면 된다.
- 생성형 AI 안내서의 기업용 API·DPA 비교표, 학습 opt-out 재고지 예시, p.46 유형별 고려사항은 **이 광고 SDK 건의 점검표가 아니다.** 색 구분 없는 텍스트만으로 그 표의 모든 칸을 법적 의무로 읽지 않는다.

## 6. 근거 (인용 범위만)

**개인정보 보호법 (제공 스냅샷, 시행 2025-10-02, 법률 20897호)**  
**[공식 원문 발췌] [VERIFIED]** — 제공된 법령 스냅샷 확인. 직접 공식 사이트 확인 아님.

- 제15조: 동의 등 수집·이용 근거, 동의 시 고지사항. 식별 행태정보 처리의 적법 요건을 정책방안이 이 조에 연결한다. 제22조 본문은 이번 발췌에 없다.
- 제26조: 위탁은 목적 외 처리 금지·보호조치 등을 문서로, 수탁자 공개, 홍보·판매 권유 위탁 시 고지, 감독, 수탁자의 범위 초과 이용 금지. 이 건의 벤더 관계가 위탁인지는 미확인.
- 제28조의8: 국외 제공·위탁·보관의 원칙적 금지와 예외. 벤더 위치 사실이 없어 적용하지 않음.
- 제29조: 안전조치. 이번 쟁점의 핵심은 철회 경로이지 안전조치 세부가 아님.

## 7. 검토자용 한 줄

출시 차단 여부는 “UI가 꺼졌는가”가 아니라 **철회 이용자의 구매 이벤트가 새 벤더에 광고 목적으로 남는가**와 **벤더가 그 데이터로 독자 최적화를 하는가**다. 둘 다 아직 로그·계약으로 닫히지 않았다. 성능 계측은 이 문장 밖에 둔다.

확인되지 않은 범위: 실제 전송 여부, suppression의 대상·목적·시각, 위탁/제공 구분과 독자 최적화, 구매 이벤트의 개인정보 해당 여부, 국외이전, 파기 조문의 현행 문언. 이 칸을 채우기 전에는 적법·위법, 준수·미준수를 쓰지 않는다.
