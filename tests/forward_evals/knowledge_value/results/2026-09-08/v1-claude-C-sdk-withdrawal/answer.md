- **작성일 / 기준일:** 2026-09-08
- **수신:** 앱 개발팀, 개인정보 담당자(CPO 라인)
- **목적:** 신규 광고 SDK 전환 시 "맞춤형 광고 끄기"가 실제로 어디까지 적용되는지 현재 증거로 확정 가능한 범위를 정리하고, 출시 전후 조치를 합의하기 위함
- **성격:** 내부 검토용 초안. 대외 송부(벤더 공문, 처리방침 공개 문구, 이용자 고지)는 법무 검토 후 확정

- 근거 자료는 ① 개인정보 보호법 스냅샷 발췌(시행 2025-10-02, 법률 제20897호), ② 「맞춤형 광고에 활용되는 온라인 행태정보 보호를 위한 정책 방안」(2024.1) 발췌, ③ 「생성형 AI 개발·활용을 위한 개인정보 처리 안내서」(2025.8) 발췌 **뿐**입니다.

- ③ AI 안내서는 생성형 AI 맥락 문서이며, 광고 SDK에 직접 적용되는 규범이 아닙니다. 이 메모에서는 **계약·DPA에서 무엇을 확인할지에 대한 참고 축**으로만 인용했습니다. 안내서 붙임 표(인쇄 46쪽)는 원본에서 색상으로 법적 의무와 자율적 책무를 구분하는데 추출 텍스트에는 색이 보존되지 않으므로, 표의 개별 항목을 모두 법정 의무로 읽지 않았습니다.

## 1. 현재 증거로 가능한 판단

### 1-1. "화면 표시 + 벤더 회신"만으로 철회 이행 완료를 확정할 수 없다

확인된 사실은 세 가지입니다: (a) 앱 화면에 철회 완료가 표시됨, (b) 신규 SDK의 광고 설정이 꺼짐, (c) 벤더가 "suppression 적용 완료" 회신. 이 세 가지는 모두 **클라이언트 설정 상태와 벤더의 자기 진술**이며, 서버의 기존 이벤트 수신기가 구매 이벤트를 신규 벤더로 전송하는 경로가 멈췄다는 증거가 아닙니다. 이번 점검에서 **실제 전송 로그를 받지 못했다**는 것이 현 상태이므로, 서버 경로의 처리 중단 여부는 **미확인**입니다.

벤더 회신도 대상 식별자·목적·적용 시각이 적혀 있지 않아, `suppression`이 (i) 광고 노출 중지인지 (ii) 신규 수집 중지인지 (iii) 이미 보관 중인 데이터의 이용 중지인지 특정할 수 없습니다. **`opt-out`, `suppression`, `delete`는 의미·범위·적용 시점이 서로 다를 수 있으므로** 벤더 원문으로 구별해야 합니다.

→ **제품팀의 "화면과 회신만으로 충분하다"는 입장은 현재 증거로 지지되지 않습니다.** 다만 이는 "위반이 확인되었다"는 뜻도 아닙니다. 확인 대상이 남아 있다는 뜻입니다.

### 1-2. 구매 이벤트의 개인정보 해당성은 아직 확정할 수 없고, "아니다"를 전제로 진행해서도 안 된다

정책 방안(인쇄 18쪽)은 ▲식별자를 매개로 자사 회원정보와 결합·이용되면 개인정보에 해당한다고 본 사례와, ▲랜덤 온라인 식별자를 쓰고 행태정보에 개인정보가 포함되지 않으며 합리적으로 고려할 때 다른 정보와 쉽게 결합해 특정 개인을 알아볼 수 없으면 개인정보로 볼 수 없다는 사례(사례③)를 함께 제시합니다.

커머스 앱의 **구매 이벤트는 회원 계정·주문 정보와 결합될 여지가 구조적으로 큽니다.** 다만 실제 전송 필드와 식별자 종류를 보지 못했으므로 해당성 판단은 유보합니다. 실무 결론은 하나입니다: **전송 로그로 필드를 확인하기 전에는 "개인정보가 아니다"를 전제로 한 설계·릴리즈 판단을 하지 않습니다.**

### 1-3. 벤더의 법적 지위가 미확정이라 적용 조문 자체가 갈린다

계약상 **벤더의 독자적인 광고 최적화 허용 여부가 확인되지 않았습니다.** 이는 단순 계약 문구 문제가 아니라 적용 규범이 갈리는 분기입니다.

- 위탁 구조라면 보호법 제26조가 적용됩니다: 위탁 문서에 목적 외 처리 금지·안전조치 사항 포함(제1항), 위탁 업무 내용과 수탁자 공개(제2항), 홍보·판매 권유 업무 위탁 시 정보주체 고지(제3항), 교육·감독(제4항), **수탁자의 위탁 범위 초과 이용·제3자 제공 금지(제5항)**, 재위탁 시 위탁자 동의(제6항).
- 벤더가 우리 목적을 넘어 **자사 광고 최적화에 재이용**한다면 제26조 제5항과 충돌하거나, 애초에 위탁이 아닌 다른 구조(제공 등)로 봐야 할 수 있습니다. 제17조 등 관련 조문 본문은 번들에 없어 그 요건은 확인 불가입니다.

→ **계약·DPA 확인 전에는 이 사안을 "위탁이니 문제없다"로도, "제공이니 동의 필요"로도 결론짓지 않습니다.**

### 1-4. "모든 이벤트와 모든 보존 데이터 즉시 삭제"도 현재 증거로 지지되지 않는다

번들 어디에도 맞춤형 광고 철회 시 **모든 이벤트와 모든 보존 데이터를 즉시 전면 삭제해야 한다는 근거는 없습니다.** 정책 방안이 제시하는 축은 사후 거부·처리 중지(개인 식별 처리 시 법 제37조 인용)이며, 이는 **목적별 처리 중지**의 문제이지 데이터 존재 자체의 전면 삭제와 동일하지 않습니다. 거래·구매 기록의 다른 보유 근거(계약 이행 등)가 있을 수 있으나 관련 법령이 번들에 없어 판단 불가입니다.

실무적으로도 지금 시점의 전면 삭제는 **1-1의 미확인 쟁점(실제 전송 여부)에 대한 증적을 없앨 수 있어 위험합니다.** 우선순위는 ① 증적 보전 → ② 목적별 처리 중지 → ③ 확인 결과에 따른 삭제·파기 범위 결정입니다.

### 1-5. 현재로서 유출 통지·신고(제34조) 트리거는 확인되지 않았다

이번 사안은 분실·도난·유출로 확인된 사실이 없습니다. 다만 전송 로그 확인 결과 철회 이후에도 범위를 벗어난 전송이 있었던 것으로 드러나면 성격을 다시 평가해야 하며, 그 판단은 로그를 본 뒤에 합니다.

### 1-6. 차단 우회로 읽힐 수 있는 지점이 SDK 교체에 내재한다

정책 방안(인쇄 22쪽)은 사후 통제권 항목에서 **맞춤형 광고를 거부한 기기 또는 웹·앱에 대해 다른 방식으로 맞춤형 광고용 온라인 식별자를 생성하는 행위(차단 우회)를 금지**한다고 서술합니다. 다만 해당 항목(❸)은 상위 분류에서 **(권고)로 표기**되어 있으므로, 이 문장을 곧바로 독립된 법정 금지의무로 단정하지는 않습니다. 그럼에도 **SDK를 교체하면서 신규 SDK가 거부 상태 기기에 새 식별자를 생성·조합하면 우회로 보일 위험이 큽니다.** 출시 전 반드시 실측 확인이 필요합니다.

## 2. 광고 철회와 집계 성능 계측의 구별

성능 계측은 **개인·기기 식별자 없이 재식별할 수 없는 집계값만 내부 시스템에서 처리하며 외부 벤더 전송이 없다는 사실이 확인**되었습니다. 이 사실관계 하에서는 정책 방안의 "개인을 식별하지 않고 처리" 축(사례③ 및 인쇄 21쪽)에 해당하므로, **맞춤형 광고 철회 신호의 적용 대상으로 자동 편입하지 않습니다.** 즉, 광고를 껐다는 이유로 성능 계측을 중단해야 한다는 결론은 나오지 않고, 성능 계측이 돌아간다는 이유로 철회 미이행이라는 결론도 나오지 않습니다.

두 축은 아래 네 가지로 구별합니다.

| 구별 축 | 맞춤형 광고 (철회 대상) | 집계 성능 계측 (현재 확인된 사실 기준) |
|---|---|---|
| 처리 목적 | 맞춤형 광고 노출·최적화 | 서비스 성능 진단·품질 개선 |
| 식별자·결합 | 광고 식별자·회원 정보 등 결합 가능성 존재(전송 필드 확인 필요) | 개인·기기 식별자 없음, 재식별 불가 |
| 외부 전송·접근 | 신규 벤더로 전송 경로 존재(실측 미확인) | 외부 전송 없음, 내부 시스템만 |
| 이용자 통제권 | 사후 거부·처리 중지의 대상 | 동일한 철회 신호를 자동 적용하지 않음 |

**이 구별이 유지되기 위한 조건**(하나라도 깨지면 판단이 바뀝니다):

1. 정책 방안이 (의무)로 명시한 **결합 금지** — 개인정보 처리 시스템과 분리 운영하고, 결합되는 매칭키가 없어야 합니다. 성능 이벤트에 회원ID·ADID를 붙이거나 광고 데이터와 조인하는 순간 이 축은 무너집니다.
2. 누적·중첩·결합으로 식별 가능성이 발생하지 않을 것.
3. 성능 계측 산출물을 **광고 타게팅·최적화에 재이용하지 않을 것.** 재이용이 생기면 목적이 광고로 이동합니다.
4. "성능 계측"이라는 이름으로 광고용 식별자를 실어 나르지 않을 것.

**UI 문구도 두 축이 구별되게 써야 합니다.** 현재처럼 "철회 완료"만 표시하면 이용자가 앱 내 모든 데이터 처리 중지로 읽을 수 있고, 반대로 서버 전송이 남아 있으면 표시가 실제보다 넓게 읽힙니다. 문구는 실제 적용 범위에 맞춰 조정합니다.

> 참고로 커머스 앱의 상품 추천은 정책 방안(인쇄 22쪽)의 **맞춤형 정보추천 서비스**(서비스 내용과 본질적으로 동일하고 이용자가 합리적으로 예측 가능한 경우) 축과 광고 축이 갈릴 수 있습니다. 다만 자사·타사 광고 노출은 광고입니다. 이번 검토 범위 밖이나 별도 정리 권장.

## 3. 남은 확인 항목

우선순위 순입니다. 아래 항목 목록은 **내부 확인용이며 법정 필수 양식이 아닙니다.**

**A. 서버 전송 경로 (최우선, 출시 게이트)**
1. 기존 이벤트 수신기 → 신규 벤더 전송이 실제로 발생하는가. 전송 로그 또는 네트워크 캡처 원본 확보.
2. 전송되는 필드 목록과 식별자 종류(ADID, 회원ID, 해시값, 주문번호 등), 결합 가능성.
3. 철회 신호가 서버 파이프라인에 반영되는 지점이 있는가. 앱 로컬 설정 → 서버 사용자 속성 → 전송 필터 중 어디가 끊겨 있는가.
4. 철회 계정과 비철회 계정을 대조한 실측 표본.

**B. 벤더 회신 구체화**
5. `suppression`의 대상 식별자 종류와 범위, 적용 목적(노출 중지 / 수집 중지 / 보관 데이터 이용 중지), 적용 시각.
6. 부분 실패 여부와 처리 방법, 재활성화 조건(예: 새 세션, SDK 재초기화, 리모트 컨피그 변경 시).
7. 기존 보관 데이터의 처리 방침.

**C. 계약·DPA**
8. 벤더 지위(수탁자 / 제공받는 자)와 **독자적 광고 최적화 허용 여부** — 제26조 제5항 관련.
9. 목적 제한, 재위탁(제6항) 통제, 파기, 감사·관리감독 조항. AI 안내서(인쇄 24쪽)의 계약 확인 항목(입력데이터 소유권·재이용 제한·안전조치·데이터 파기)은 **참고 목록**으로 활용.
10. **국외이전 해당 여부** — 벤더 서버 소재지 및 국외 조회 가능성. 해당 시 제28조의8 각 호의 근거와 제2항 고지사항, 처리방침 공개 또는 개별 고지 여부 확인.

**D. 클라이언트·투명성**
11. 신규 SDK가 거부 상태 기기에 **새 식별자를 생성·조합하지 않는지** (1-6 우회 축).
12. 구 SDK 잔존·병행 기간 중 중복 전송 여부, 잔존 초기화 코드.
13. 처리방침 기재 — 제3자 수집도구의 명칭·종류, 수집 주체, 항목, 목적, 통제방법. 정책 방안(인쇄 25쪽)은 웹·앱별 분리 기재를 **권고**합니다.
14. 앱의 주된 이용 대상에 14세 미만 아동이 포함되는지(인쇄 26쪽 권고 축).

**E. 법령 범위**

## 4. 출시 전 조치 (게이트)

1. **A항목 1~4를 확보하기 전까지, 신규 벤더로의 서버측 전송은 기본 비활성 또는 철회 사용자 전량 제외 상태로 고정.** 이 상태를 릴리즈 조건으로 둡니다.
2. 철회 신호를 **단일 소스로 확정**하고(앱 로컬 설정 + 서버 사용자 속성 동기화), 이벤트 발송 직전 한 지점에서 필터링. 클라이언트 SDK 설정과 서버 전송 조건이 각자 판단하지 않도록 합니다.
3. 신규 SDK의 식별자 생성 동작을 거부 상태에서 실측 확인(1-6).
4. 구 SDK 제거·비활성 확인, 병행 기간 중복 전송 확인.
5. **벤더 서면 재확인(B항목 5~7) 수령 전까지 "철회 완료" UI 문구 재검토.** 표시 범위를 실제 적용 범위에 맞춥니다.
6. 처리방침·이용자 고지 문안 갱신 초안 작성 → **법무 검토 후 공개.** (대외 문구이므로 이 메모 단계에서 확정하지 않습니다.)
7. **증적 보전 지침 시행:** 관련 로그·설정 이력·벤더 회신을 보전하고, 확인 완료 전 전면 삭제를 유예합니다. 이 지침을 "삭제하지 말라"가 아니라 "확인 전까지 보전하고 처리는 중지한다"로 팀에 전달합니다.
8. 계약·DPA 검토 결과에 따라 필요 시 특약(목적 제한, 독자 최적화 금지, 재위탁 통제, 파기·감사) 협의 착수.
